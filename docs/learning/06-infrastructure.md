# Phase 6 — infrastructure

**Goal:** ship the "real backend" artifacts the local stand-ins model, so the
project shows it understands how it scales — without requiring any of it to run.

## What got built

```
Dockerfile               multi-stage image (uv build -> slim runtime, non-root, healthcheck)
.dockerignore
Makefile                 install / test / lint / serve / demo / docker / clean
deploy/
  docker-compose.yml     platform service + volume; optional MLflow (commented)
  airflow/fine_tune_dag.py   the DAG form of the orchestrator
  k8s/platform.yaml          the control plane on K8s (Namespace/PVC/Deployment/Service)
  k8s/model-serving.example.yaml   sample output of ftp.deploy.k8s (vLLM + LoRA + canary)
  README.md              the local→real mapping table + run instructions

```

## Ideas

### The whole phase is "documentation as code"
None of this is needed to run the platform. Its value is showing the *scale-up
path*. The key discipline (ADR 0004): the real backends run the **same `ftp`
code** as the local ones. The Airflow DAG's `prepare/train/evaluate/register`
tasks call the same functions `run_job` calls; the K8s model-serving manifest is
literally generated by the same `ftp.deploy.k8s.render_manifests` the app uses.
No second implementation to drift.

### Multi-stage Docker with uv
The `builder` stage resolves dependencies into a venv with `uv sync --frozen
--no-dev`; the `runtime` stage copies just that venv + source into a slim image,
runs as a non-root user, and has a healthcheck hitting `/health`. Copying
`pyproject.toml`/`uv.lock` before the source means dependency layers cache across
code changes.

### SQLite ⇒ single control-plane replica
`k8s/platform.yaml` runs **one** API replica, on purpose: the control-plane state
is SQLite, a single-writer store. The manifest comments say how you'd scale out
(swap the DB URL for Postgres). Naming the constraint is better than pretending it
isn't there.

### Canary is just two annotations
`model-serving.example.yaml` (generated, not hand-written) shows the canary
deploy from the plan compiles down to
`nginx.ingress.kubernetes.io/canary-weight: "10"`. Seeing the generated YAML makes
the abstract "route 10% of traffic" concrete.

## Where the plan landed

Every box in the plan's architecture diagram now maps to code:

- **API (FastAPI)** → `src/ftp/api` ✓
- **Data validation pipeline** → `src/ftp/data` ✓ (the differentiator)
- **Training orchestrator (Airflow)** → `orchestrator.py` (local) + `deploy/airflow` ✓
- **Model registry (MLflow)** → `registry/` (local) + compose MLflow note ✓
- **Deployment (Kubernetes)** → `deploy/` local + `k8s/` ✓ (canary included)
- **Dashboard** → `frontend/` ✓ (status, live loss curves, base-vs-fine-tuned,
  cost, leaderboard)
